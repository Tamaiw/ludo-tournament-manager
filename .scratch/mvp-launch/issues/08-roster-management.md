# 08: Roster management (manager add-by-user, self-register, withdraw)

**What to build:** A tournament's roster is the list of registered players. Three ways to fill it: (1) **manager adds an existing user by id** via `POST /tournaments/{id}/roster/add` (works in `invite_only` mode, requires `draft` or `registration_open` status, below `max_players`); (2) **authenticated user self-registers** via `GET /tournaments/{id}/register` + `POST /tournaments/{id}/register` (works only in `self_register` mode, `registration_open` status, below `max_players`); (3) **platform invite auto-adds** when the invitee accepts (T07 wires the email; this ticket wires the auto-add: `accept_invite` checks if there's a pending invite with the same email for any tournament in `invite_only` mode that has the accepting user in `tournament_player`... actually re-reading: the spec says "send a platform invite that auto-adds the new user to the roster when accepted" — so `invite_user` should also take a tournament ID and add a pending-roster marker; on accept, the user is added to the roster). **Withdrawal** via `POST /tournaments/{id}/roster/{playerID}/withdraw` — a player can withdraw themselves; a manager can withdraw any player. **Manager remove** via `POST /tournaments/{id}/roster/remove` — same as withdrawal but only by the manager. The roster page at `GET /tournaments/{id}/roster` shows the current list, with manager-only actions. All state changes write audit log rows. The downstream-lock rule does not apply pre-bracket (the bracket doesn't exist yet).
